# jobhunter

Автоматизация поиска работы: сбор вакансий (55 проверенных Telegram-каналов,
автопоиск новых, ATS-фиды компаний, 11 job-бордов, careered.io, HN) →
персональное резюме и письмо под каждую вакансию с проверкой на выдумки →
рассылка в Telegram и на email → ведение переписки → согласование интервью с
владельцем и запись в Google Calendar.

Работает локально: три контейнера Docker, пульт — личный бот в Telegram.

## Telegram: отправляю сам

Команда `/outreach` в личном боте запускает пошаговый сценарий: **одна вакансия,
ник рекрутёра, готовое сообщение и PDF-резюме прямо в Telegram**. Браузер не нужен.
Кнопка «Открыть @ник с текстом» использует
[официальную ссылку Telegram с черновиком](https://core.telegram.org/api/links#public-username-links):
она открывает чат и подставляет текст, но не отправляет его. Если клиент не
подставил текст, используй «Текст отдельно» и скопируй полученное сообщение.
«Ник отдельно» и «📎 Получить резюме» также работают внутри бота.

После «✅ Всё отправил → следующий» подтверди «Окей, всё отправил». Бот сохранит
отметку и сам пришлёт следующий отклик. Отметка и постановка следующей карточки
в очередь выполняются одной транзакцией; повторное нажатие не выдаст другой
отклик повторно. Уже выданная пятёрка не теряется: бот последовательно предлагает
её оставшиеся карточки. После неё резервируется только одна новая вакансия.

Резюме доставляется через [sendDocument](https://core.telegram.org/bots/api#senddocument)
только в настроенный личный чат владельца, не в группы и не рекрутёру. Если
задан `BASE_CV_PATH`, используется именно это основное резюме; иначе PDF из
карточки. Пути ограничены папками резюме, формат и размер проверяются перед
чтением. Ошибка доставки файла видна владельцу, а не скрывается успешной отметкой.
Устаревшие карточки перепроверяются перед доставкой.

[Веб-очередь](http://127.0.0.1:8765/manual-telegram) остаётся дополнительным
интерфейсом на ПК. Выдача в боте продолжается по твоим отметкам, а не по новому
автоматическому расписанию.

После реальной отправки нажми «Я отправил» и подтверди. Это запись **со слов
владельца**, а не подтверждение доставки Telegram: идентификатор сообщения и
успешная запись API-журнала не выдумываются. Входящие по отмеченному диалогу
попадают в обычное чтение; автоответы и автоматические напоминания для переданных
владельцу заявок запрещены даже после снятия общего ручного режима.

«Не подходит» убирает карточку и предлагает следующую. «Не получилось» убирает
её без повтора и приостанавливает выдачу; возобновить её можно по `/outreach`.
Повторная команда показывает текущий отклик, не резервируя ещё одну вакансию. Непроверенные,
уже отправленные и неоднозначные попытки в новую подборку не включаются;
повторные контакты исключаются по Telegram-имени, даже без `employer_id`.
Ограничения Telegram могут мешать и ручной отправке — это не способ их обойти.

## Что нужно один раз

**1. Telegram API** — https://my.telegram.org → API development tools → создать
приложение. `api_id` и `api_hash` вписать в `.env`. Затем:

```bash
python -m jobhunter.outreach.sender --login
```

Telegram пришлёт код подтверждения — вводишь сам. Создастся `jobhunter.session`
(лежит в `.gitignore`: утечка этого файла = полный доступ к аккаунту).

**2. Gmail** — Аккаунт Google → Безопасность → Двухэтапная аутентификация →
Пароли приложений. Полученный пароль в `.env` → `SMTP_APP_PASSWORD`.
Обычный пароль от почты не подойдёт и не нужен.
`SMTP_PORT=587` использует STARTTLS, `SMTP_PORT=465` — TLS сразу при
подключении. Если порт 587 недоступен в вашей сети, укажите 465 в `.env`
и пересоздайте контейнеры: `docker compose up -d`. Оба режима проверяют
сертификат сервера; отправка пароля без TLS запрещена.

**3. Токен careered.io** уже в `.env`. Если ingest скажет `AUTH LOST` — зайди на
careered.io, F12 → Application → Local Storage → `access_token`, обнови значение.

## Автопилот — система работает сама

Штатный способ — в Docker (см. ниже). Напрямую, без контейнеров:

```bash
python -m jobhunter.autopilot
```

Расписание (Москва): 09:30 расширенный сбор вакансий → 10:00 подготовка
откликов → 10:15 авто-одобрение (скор ≥55 и пройденный гейт) → 10:30 email →
11:15 Telegram → 13:30 повторный сбор Telegram-лент → 16:40 Telegram →
18:30 повторный сбор Telegram-лент → 20:00 итог дня в лог.
Входящие проверяются каждые 20 минут с 9 до 21, календарь Google
досинхронизируется каждые 4 часа.

Проверить цикл без отправки:

```bash
python -m jobhunter.autopilot --once --no-send
```

Лог: `logs/autopilot.log`. Остановить: Ctrl+C или стоп-файл.

**Роль языковой модели ограничена**: живой язык писем и черновики ответов
рекрутёрам. Каждый её текст проходит анти-фабрикация гейт — техтермины,
цифры и годы сверяются с profile.yaml, и при любом «улучшении» биографии
текст отклоняется. Без ключей LLM всё работает на шаблонах.

## Запуск в Docker

```bash
docker compose up -d
```

Четыре сервиса: `migrate` (создаёт схему и выходит), `autopilot` (сбор,
отправка, переписка), `bot` (пульт в Telegram), `web` (дашборд на
`127.0.0.1:8765`). Все с `restart: unless-stopped` — после перезагрузки
Windows поднимаются сами, если в Docker Desktop включён автостарт
(Settings → General → Start Docker Desktop when you sign in).

```bash
docker compose ps            # состояние и healthcheck
docker compose logs -f bot   # что делает бот
docker compose down          # остановить
```

**Где что лежит.** База SQLite и сессия Telegram — в томе `jobhunter-data`:
на смонтированной папке Windows файловые блокировки SQLite ненадёжны, а это
прямой путь к «database is locked» и повреждению базы. Всё, что нужно
открывать глазами — резюме, логи, календарь, — в папке `./out` рядом с
проектом.

**Важно.** Пока контейнеры работают, не запускай `python -m jobhunter...` с
хоста: второй Telethon-клиент на той же сессии даёт `AuthKeyDuplicatedError` и
разлогинивает аккаунт, а PID-лок отправителя хостовый процесс не увидит —
пространства процессов у контейнера и Windows разные. Ручные прогоны:

```bash
docker compose exec autopilot python -m jobhunter.ingest.discover --list
```

Чтобы эта ошибка не могла случиться по невнимательности, база и сессия
убраны из корня проекта (остались как `*.moved` и в `backup_*/`). Запуск с
хоста теперь создаст пустую базу вместо того, чтобы писать в рабочую
параллельно контейнеру — безопасный отказ вместо тихого расхождения данных.

**Автозапуск и резервные копии.**

```bash
powershell -ExecutionPolicy Bypass -File scripts\start.ps1
powershell -ExecutionPolicy Bypass -File scripts\backup_volume.ps1
```

`start.ps1` ждёт, пока после входа в систему поднимется Docker Desktop, и
запускает проект — ярлык на него кладётся в `shell:startup`.
`backup_volume.ps1` сводит WAL и складывает том в `backup\*.tgz`, храня
последние восемь копий: том живёт внутри WSL2 и исчезнет вместе с
переустановкой Docker, а архив лежит на обычном диске. Проверить последний
архив можно так:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\verify_backup.ps1
```

Операционные команды:

```bash
python -m jobhunter.ops check
python -m jobhunter.ops export --path out/export.json
python -m jobhunter.ops restore --source backup.db --target restored.db
python -m jobhunter.ops close-stale --days 45 --apply
```

`restore` сначала выполняет SQLite `integrity_check` и пишет в отдельный
target-файл. Рабочая БД не перезаписывается автоматически.

## Бот-пульт в Telegram

Личный бот от BotFather: статистика, кнопки вместо команд, уведомления.

Экраны: главный (квота дня, воронка, что ждёт решения), статистика с графиком
отправок по дням, воронка по статусам, очередь на отправку с кнопкой
«одобрить топ-10», ближайшие интервью, каналы-источники. Бот держит одно
сообщение-экран и правит его — чат не превращается в ленту сводок. Веб-
дашборд дополнительно умеет фильтровать очередь, открывать полную историю
заявки, показывать здоровье источников и управлять blacklist работодателей.
Read-only API: `/api/summary` и `/api/applications`. В `/api/summary` поле
`telegram` показывает число активных каналов, свежесть прохода и ошибки по
каналам.

Карточки на решение приходят с кнопками: `✅ пт 29.08 16:00`, `🕒 Другое
время`, `❌ Не подходит` вместо `/ok 12`. Нажатие принимается мгновенно, а
сообщение рекрутёру уходит в течение пяти минут: писать может только процесс
с личной сессией Telegram, поэтому бот кладёт решение в очередь, а исполняет
автопилот. Результат дописывается в ту же карточку.

Уведомления: рекрутёр ответил, назначено интервью, сработал стоп-кран,
PeerFlood, исчерпана квота, вечерняя сводка.

Настройка — три строки в `.env`:

```
TELEGRAM_BOT_TOKEN=...      # от @BotFather
BOT_ALLOWED_USER_IDS=...    # свой id: написать @userinfobot
OWNER_CHANNEL=bot           # bot | saved | both
```

Пустой `BOT_ALLOWED_USER_IDS` — бот не выполняет ничего. Он управляет
отправкой от твоего лица, поэтому открытым по умолчанию быть не может; чужие
сообщения игнорируются молча.

`OWNER_CHANNEL` не удаляет «Избранное», а переключает: токен бота можно
отозвать одной командой, Telegram может заблокировать бота, Bot API может
лежать — а личный аккаунт продолжит работать. Это запасной пульт.

## Переписка и встречи

Каждые 20 минут бот читает входящие по своим заявкам и решает:

- **рутина** — отвечает сам: «пришлите резюме» (шлёт файл), «когда удобно
  созвониться» (предлагает слоты), вежливое «спасибо». Не больше 4
  автоответов на тред, только днём, с человеческой паузой;
- **предложено время интервью** — парсит слоты и шлёт карточку тебе
  в «Избранное». Рекрутёру до твоего решения не отвечает;
- **техвопрос / зарплата / оффер / непонятное** — тред уходит человеку
  (NEEDS_HUMAN): в карточке текст рекрутёра и черновик ответа от LLM,
  прошедший гейт. Отправится только по твоей команде;
- **отказ** — закрывает заявку.

Команды в «Избранном» (Saved Messages) своего же аккаунта:

```
/ok 12          подтвердить вариант 1 из карточки   /ok 12 2 — вариант 2
/time 12 29.08 16:00   назначить своё время
/no 12          отказаться от предложенного времени
/send 12        отправить черновик как есть
/say 12 текст   отправить свой текст
/skip 12        закрыть карточку без действий
/status         сводка   /stop и /go — стоп-кран   /help — подсказка
```

После `/ok` или `/time`: подтверждение уходит рекрутёру, интервью пишется
в БД, событие создаётся в Google Calendar (с Google Meet и напоминаниями
за сутки и за час), плюс обновляются `interviews.ics` и `INTERVIEWS.md`.
Карточка без ответа протухает через 12 часов (OWNER_DECISION_TTL_HOURS).

**Google Calendar — разовая настройка.** Google Cloud Console → новый проект →
включить Calendar API → OAuth-клиент типа **Desktop app** → скачать JSON как
`google_client_secret.json` в корень проекта. Затем на хосте (в контейнере нет
браузера, а вход требует его):

```bash
pip install google-api-python-client google-auth-oauthlib
```

```bash
python -m jobhunter.schedule.gcal --login
```

Полученный токен положить в том, откуда его читают контейнеры:

```bash
docker run --rm -v jobhunter-data:/data -v "C:/Users/User/Desktop/jobhunter:/src:ro" alpine sh -c "cp /src/google_token.json /data/ && chown 10001:10001 /data/google_token.json"
```

Сам `google_client_secret.json` в контейнер не нужен и в образ не попадает:
`client_id` и `client_secret` лежат внутри токена, и обновлять доступ он умеет
сам. Проверка:

```bash
docker compose exec autopilot python -m jobhunter.schedule.gcal --test
```

Без этой настройки всё работает — останутся `.ics`-файл и карточки.

## Ручной цикл

Когда система работает в Docker, все ручные команды идут через `exec` — иначе
получится второй процесс на той же базе и той же сессии Telegram:

```bash
docker compose exec autopilot python -m jobhunter.ingest.all_sources
docker compose exec autopilot python -m jobhunter.pipeline
docker compose exec autopilot python -m jobhunter.outreach.approve --list
docker compose exec autopilot python -m jobhunter.outreach.approve --show 260
docker compose exec autopilot python -m jobhunter.outreach.approve --all
docker compose exec autopilot python -m jobhunter.outreach.sender --dry-run
docker compose exec autopilot python -m jobhunter.outreach.sender
docker compose exec autopilot python -m jobhunter.outreach.mailer
```

Без Docker те же команды запускаются напрямую (`python -m jobhunter...`), но
тогда контейнеры должны быть остановлены: `docker compose down`.

## Два канала отклика

**Автоматический** — где работодатель сам опубликовал контакт (Telegram-хендл
или почту в тексте вакансии). Система пишет и отправляет.

**Ручной** — вакансии из ATS-фидов: Databricks, GitLab, Linear, Grafana Labs,
Brex. Отклик там через форму компании. Система оценивает, готовит персональное
резюме и даёт ссылку — остаётся приложить файл и отправить.

```bash
docker compose exec autopilot python -m jobhunter.manual_apply --top 30
```

Список: **http://127.0.0.1:8765/manual**

Формы намеренно не автозаполняются: там отсеивающие вопросы (право на работу,
опыт в годах, релокация), и неверный автоответ закрывает компанию навсегда.

## Стоп-кран

```bash
type nul > STOP_SENDING.flag
```

Проверяется **перед каждым** сообщением, не раз на партию. Удалить файл — работа
возобновится.

## Следы работы бота

**Папка в Telegram.** Каждый диалог, куда бот написал, кладётся в отдельную
папку-вкладку (по умолчанию «Работа» 💼). «Избранное» остаётся каналом
управления — там только карточки на решение и команды, они не тонут в
переписке по вакансиям. Выключается `TG_FOLDER_ENABLED=false`.

**Архив на диске** — `logs/sent/YYYY-MM-DD.md` и `.jsonl`: кому, когда, что
написали и с каким резюме. Переживает и удаление сообщений, и пересоздание
базы. Выключается `SENT_ARCHIVE_ENABLED=false`.

```bash
docker compose exec autopilot python -m jobhunter.ingest.ats --check   # живы ли провайдеры
python -m jobhunter.ingest.ats --list    # реестр компаний
```

Реестр досок пополняется вручную: находишь компанию → её страница вакансий →
берёшь токен из URL → добавляешь в `REGISTRY` в `jobhunter/ingest/ats.py`.
Эндпоинты меняются молча, поэтому есть канареечная проверка.

Не подключены намеренно: RemoteOK (robots.txt запрещает ботов по имени), Хабр
Карьера (ToS запрещает воспроизведение контента), Djinni/getmatch (контакты за
логином), LinkedIn Easy Apply боты (нарушают §8.2 пользовательского соглашения
и ведут к блокировке аккаунта), Apollo / Hunter / RocketReach / Lusha и прочие
базы контактов (персональные данные собраны без согласия — GDPR, и это
инструменты холодного спама, а не поиска работы).

### Оговорка по Telegram-каналам

`t.me/robots.txt` отсутствует (HTTP 404), но **условия Telegram содержат более
общий запрет**: telegram.org/tos/content-licensing — доступ к пользовательскому
контенту для целей, отличных от обычного использования платформы, запрещён, и
отдельно упомянуты *scraping, indexing, harvesting, aggregation*.

Мы читаем публичные веб-превью каналов как обычный посетитель. Смягчение:
браузерный User-Agent, не чаще 1 запроса в 2 секунды, один обход в сутки,
сохраняем только посты вакансий, никакого корпуса и обучения моделей. Риск не
нулевой — решение принимается осознанно.

### Защита от постов-резюме

Существуют каналы, на 100% состоящие из резюме **соискателей**, а не вакансий.
Контакт там тоже есть, и наивный парсер его берёт — после чего система пишет
другому кандидату, приняв его за рекрутёра. Фильтр `_RESUME_POST` в
`ingest/tgchannels.py` отсекает такие посты; хендлы каналов и их кросс-промо
семейств лежат в `CROSS_PROMO`; почтовые домены (`@gmail` из `ivan@gmail.com`)
— в `HANDLE_STOPLIST`.

## Защита от вранья в резюме

Единственный источник фактов — `profile.yaml`. Генератор может выбирать,
переставлять и переформулировать записанное там, но не добавлять. Перед тем как
попасть в очередь на отправку, каждое резюме и письмо проходит гейт
(`jobhunter/tailor/gate.py`), который проверяет:

1. **провенанс** — каждый буллет восходит к записи профиля (похожесть ≥ 0.60);
2. **числа** — каждая цифра подтверждена метрикой, датой или стажем;
3. **лексикон** — технологии только из профиля; `never_claim` (C#, .NET,
   GitHub Actions, Java, Go…) блокируются везде;
4. **утечка терминов работодателя** — что всплыло из текста вакансии, видно в
   `promoted_terms`;
5. **годы** — заявленный стаж сходится с таймлайном, стаж по навыку не завышен;
6. **сущности** — компании только из реального опыта;
7. **письмо** наследует те же правила.

Любое нарушение → `GATE_FAILED`, отправка невозможна. Попасть в
`PENDING_APPROVAL` можно только через `Application.transition()` с пройденным
гейтом. Тесты: `python -m pytest tests/ -q` (25 состязательных кейсов).

`python validate_profile.py` — проверка самого профиля на битые ссылки и
завышенный стаж.

## Защита аккаунта Telegram

Темп: 30 холодных сообщений в день (`DAILY_COLD_LIMIT`), сессиями по 4–6 в день,
паузы логнормальные (медиана 90 с), имитация набора, окно 09:00–21:00 по времени
получателя, один контакт на работодателя раз в 30 дней.

Предохранители:
- `PeerFloodError` → немедленный стоп партии, лок 48 ч, дневной потолок пополам;
- второй `PeerFloodError` → постоянный ручной режим;
- `FloodWait` > 300 с трактуется как анти-спам сигнал, а не как задержка;
- `me.restricted` проверяется перед каждым днём отправки;
- один процесс на сессию (PID-лок) — иначе `.session` повреждается;
- `random_id` фиксируется в БД: при повторе Telegram дедуплицирует сам.

Если процесс упал после начала отправки, заявка получает
`SEND_FAILED_AMBIGUOUS` и не отправляется повторно автоматически. Сначала
проверь чат и верни её кнопкой «вернуть в очередь» на странице заявки.

## Операционная панель

В локальной панели доступны четыре экрана:

- `/sending` — конкретная причина ожидания каждой заявки, рабочая квота и
  ближайший запуск. «Не ранее» обозначает окончание задержки, а не обещание
  доставки. Без свежего пульса планировщика время считается неподтверждённым.
- `/attention` — ответы, ошибки обработки/доставки и истёкшие карточки. Кнопка
  создаёт карточку владельцу, но не отправляет сообщение рекрутёру. Отозванные
  заявки и запрещённые контакты нельзя оживить старой карточкой.
- `/reading` — результат последнего прохода каналов, рабочих Telegram-диалогов
  и папки Gmail. Остаток загрузки и незавершённый разбор учитываются отдельно.
  Нулевой остаток после сохранённой границы **не доказывает** полноту старой
  истории. При лимите страниц Telegram остаток честно обозначается неизвестным.
- `/outcomes` — непересекающиеся категории результатов за 90 дней: интерес,
  запрос CV, отказ, интервью, оффер, прочие ответы и отсутствие ответа.
  Сигнал классификатора не выдаётся за подтверждённое интервью или оффер.

JSON-версии: `/api/sending`, `/api/attention`, `/api/reading`, `/api/outcomes`.
Gmail загружается от старых UID к новым; неполная загрузка или неизвестный
UIDVALIDITY не продвигают границу. Входящие сохраняются до принятия решения;
после сбоя они остаются видны владельцу, без слепой повторной отправки.
Telegram проверяет стоп-кран и состояние заявки повторно после паузы набора.
Напоминание имеет отдельный ключ доставки и сохраняет дату первого отклика.

### Надёжность очередей

Решение владельца занимает один обработчик. Перед внешним действием сохраняется
маркер начала отправки: после аварийного завершения такой ответ не повторяется
автоматически, пока владелец не проверит доставку. Режим `dry` исполнения решений
не изменяет карточки, календарь или стоп-кран. Перед ответом состояние контакта
и ограничения перепроверяются непосредственно перед отправкой.

Очередь уведомлений атомарно выбирает и занимает записи. SMTP-партии защищены
общим файловым замком рядом с базой; завершение процесса освобождает замок.
Для дневных заданий такой же замок исключает одновременный запуск и позволяет
восстановиться после аварии без ожидания устаревшего двухчасового маркера.
Частичные ошибки источников больше не помечаются успешным дневным проходом.

### Резервные копии и секреты

Создать проверенный архив рабочего тома без остановки бота:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/backup_volume.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify_backup.ps1
# Проверить конкретную копию:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify_backup.ps1 -Archive backup/имя-копии.tgz
```

Скрипты используют существующий Docker-образ, стандартную библиотеку Python и
отключённую сеть. Рабочий том подключается только для чтения. Каждая SQLite-база,
включая Telegram-сессию, копируется через Backup API с учётом WAL. Это согласованный
снимок каждой базы, а не единая транзакция всех файлов тома. Новые архивы содержат
контрольные суммы; публикация происходит только после проверки базы и архива.
Старые архивы без манифеста также проверяются, включая их WAL.

Существующие копии не перезаписываются и автоматически не удаляются. Контролируй
место в `backup/`. Архив содержит базу, Telegram-сессию и имеющиеся Google-токены:
не публикуй его. `.env`, `profile.yaml`, `cv_base/` и `/out` находятся вне тома и
в этот архив не входят. Восстановление поверх рабочего тома намеренно не выполняется
скриптом проверки. Сначала проверяй копию изолированно.

```powershell
python -m jobhunter.repo_safety
```

Эта проверка в CI запрещает отслеживание путей секретов, БД, сессий, бэкапов и
архивов переписки. Она не сканирует содержимое и историю Git. Удаление файла из
индекса сохраняет локальную копию, но **не удаляет секрет из прежних коммитов**.
Если секреты публиковались, отдельно нужны проверка доступа, отзыв/замена токенов
и согласованная очистка истории. Не пересылай содержимое токенов в чат.
